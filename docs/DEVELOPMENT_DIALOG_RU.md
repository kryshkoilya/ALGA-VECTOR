# ALGA VECTOR — журнал разработки вместе с OpenAI Codex

Дата основного цикла: 24–26 июля 2026 года  
Авторы продукта: **Буйвол и Задира**  
Инженерный ассистент: **OpenAI Codex**

## Что это за документ

ALGA VECTOR создавался итеративно в локальной задаче Codex. Публичная ссылка
на саму локальную Codex-задачу официально не документирована: Codex хранит
отдельную локальную историю и не предоставляет подтверждённый публичный
share-URL для такого диалога.

Поэтому этот файл является публичным журналом диалога: он сохраняет запросы,
решения, исправления и проверенные результаты без публикации локальных путей,
идентификаторов оборудования и других приватных данных.

Это не дословный экспорт каждого сообщения. Формулировки сокращены, а
чувствительные и повторяющиеся детали отредактированы.

## Исходная цель

Пользователь поставил цель объединить в одном Windows-приложении:

- пассивный RF-мониторинг через tinySA, RTL-SDR и HackRF;
- внешний direction finding через отдельный валидированный DF-источник;
- акустический контур;
- гражданский ADS-B/dump1090 context;
- temporal sensor fusion;
- понятный операторский интерфейс;
- диагностируемый offline-first runtime и Windows packaging.

Ключевое требование повторялось на протяжении всей работы:

> Программа должна быть не демонстрационной картинкой, а реально запускаемым
> foundation, где оператор понимает, что происходит и почему.

## Главные этапы диалога

### 1. От инженерного макета к запускаемому приложению

Пользователь потребовал после архитектуры сразу перейти к рабочему инкременту:
PySide6 shell, dashboard, devices, fake adapters, structured logs, onboarding,
Demo и Windows packaging.

Результат:

- создан локально запускаемый PySide6 runtime;
- добавлены Live, Safe и явно маркированный Demo;
- fake adapters стали детерминированными;
- появились JSONL logs, incidents и диагностика;
- добавлены GUI/CLI PyInstaller targets и portable build.

### 2. Реальные приёмники и честные capabilities

Основной аппаратный фокус сместился на RTL-SDR, tinySA и HackRF.

Решение:

- discovery отделён от открытия устройства;
- найденное устройство требуется явно добавить и включить;
- реальные adapters работают в отдельном bounded worker;
- timeouts, reconnect и invalid handle стали видимыми состояниями;
- частотный диапазон определяется подтверждённым capability устройства;
- один приёмник не выдаётся за одновременно широкополосную систему.

### 3. Борьба с ложными RF-алертами

Пользователь сообщил, что интерфейс не объясняет разницу между устойчивым
эпизодом, фонящей рацией, шумом и одиночным всплеском.

Был воспроизведён критический дефект: один FFT-bin одного кадра мог выглядеть
как уверенное событие.

Исправления:

- покадровое измерение отделено от окончательного решения;
- добавлены temporal FSM, debounce, hysteresis и dwell;
- persistence привязан к сопровождаемому спектральному компоненту;
- attack/release имеют разные условия;
- плохие и stale данные блокируют подтверждение;
- confidence назван эвристической силой признаков, а не вероятностью;
- система может воздержаться и показать, чего не хватает.

### 4. Граница достоверности

В диалоге пользователь хотел получить точные уведомления
`дрон / рация / видеоканал`, направление и дальность.

Инженерное решение зафиксировало обязательные ограничения:

- частота и PSD сами по себе не идентифицируют физический источник;
- RSSI не преобразуется в километры;
- один RTL-SDR, tinySA или HackRF не измеряет азимут;
- один bearing не даёт координаты;
- ADS-B не является IFF;
- generic RF+acoustic correlation не равна `TARGET_CONFIRMED`;
- identity-like событие требует versioned classifier evidence и независимого
  подтверждения.

Вместо недостоверной «точности» система объясняет измеренные признаки,
ограничения и следующий безопасный шаг.

### 5. Мультисенсорный foundation

В версии 0.6.0 были объединены:

- RF decision;
- acoustic PCM feature/detection core;
- локальный гражданский `dump1090 aircraft.json`;
- optional external bearing;
- temporal sensor fusion.

Каждая модальность получила freshness, quality, provenance и abstention.

### 6. Последовательный автообзор

Для версии 0.6.1 добавлен capability-gated автообзор:

- VHF/UHF/L/S/C общие инженерные области;
- весь подтверждённый диапазон выбранного приёмника;
- отдельные baseline и temporal state для каждого окна;
- warm-up после retune;
- блокировка fallback на другой приёмник;
- видимые dwell, окно последнего кадра и ожидаемый цикл.

Интерфейс прямо предупреждает, что один SDR посещает окна последовательно и
может пропустить короткое событие.

### 7. SIMPLE MODE и EXPERT MODE

Последний крупный запрос: перестать показывать новичку waterfall, IQ,
внутренние метрики и перегруженную инженерную панель.

Архитектура 0.7.0:

```text
Sensors
  ↓
Device / Acquisition / Analysis / Fusion
  ↓
signal_processor
  ├─ normalized event schema
  ├─ fail-closed policy
  ├─ bounded unified event bus
  ├─ confidence and source attribution
  └─ human-readable interpretation + recommendation
  ↓
SIMPLE MODE / EXPERT MODE
```

SIMPLE MODE отвечает на пять вопросов:

1. Есть ли активность?
2. Что именно измерено?
3. Есть ли подтверждённый сектор?
4. Насколько сильны доступные признаки?
5. Что делать дальше?

EXPERT MODE сохраняет spectrum, waterfall, карту, направление, evidence,
диагностику и настройки.

Оба режима используют один backend. Переключение интерфейса не перезапускает
acquisition и не меняет пороги.

## Что было дополнительно исправлено при визуальном QA

- одинаковое состояние качества больше не заполняет журнал копиями;
- глобальная плашка не восстанавливает устаревший legacy-alert поверх
  нормализованной обстановки;
- Demo/manual direction не показывается как измеренный внешний bearing;
- карточка недоступного пеленга не повторяет одну фразу дважды;
- важные события можно отделить от информационного фона.
