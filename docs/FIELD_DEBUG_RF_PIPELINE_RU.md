# Полевой debug RF-тракта ALGA VECTOR

Этот чек-лист нужен, когда физический приёмник подключён, активность рядом есть,
а операторский экран молчит. Он позволяет определить, где оборвалась цепочка:

```text
DEVICE → CAPTURE → DETECTOR → NORMALIZER → EVENT BUS → SIMPLE UI
```

RF-наблюдение само по себе не доказывает тип физического объекта. Поэтому ранний
всплеск должен доходить до интерфейса как неподтверждённая RF-активность, а не
как утверждение «это точно БПЛА».

## 1. Включить подробный журнал

1. Откройте **Настройки**.
2. Выберите **Подробность журнала → DEBUG · полевой разбор тракта**.
3. Для раннего полевого обнаружения выберите
   **Чувствительность детекции → Высокая**.
4. Нажмите **Проверить и применить**.
5. Откройте **Диагностика → Полевой тракт данных**.

Для одного диагностического запуска тот же уровень можно включить без изменения
сохранённого профиля:

```powershell
& '.\ALGA VECTOR.exe' --live --debug
```

Панель должна показать:

- `ЖИВЫЕ ДАННЫЕ`, а не Demo;
- конкретный приёмник и состояние `ПОТОК АКТИВЕН` или `ГОТОВО`;
- последний RF-кадр с `source`, `seq`, возрастом и числом dropped frames;
- фактическое окно center/span;
- sample rate и применённый режим gain;
- `HIGH` и уровень журнала `DEBUG`;
- абсолютный путь к `alga-vector.jsonl`.

Если файл журнала недоступен, не начинайте контрольный пролёт: сначала исправьте
каталог данных или права на него.

## 2. Смотреть JSONL во время теста

Путь берите только из панели диагностики. В PowerShell:

```powershell
Get-Content -LiteralPath 'D:\ALGA_DATA\logs\alga-vector.jsonl' -Wait
```

Каждая строка — отдельный JSON-объект. Для одного эпизода сопоставляйте
`source_id`, `sequence`, `event_id`/`trace_id`, center/span и timestamp.

Ключевые этапы и уже используемые имена событий:

| Этап | Что искать | Что означает отсутствие |
|---|---|---|
| DEVICE | `runtime.started`, `device.receiver_unavailable`, состояние устройства | адаптер не открыт или запущен не Live-профиль |
| CAPTURE | `acquisition.capture_requested`, `acquisition.frame_captured`, `acquisition.capture_failed` | запрос не принят worker либо IQ/sweep не дошёл от драйвера |
| TUNING | `spectrum.frame_tuning_mismatch`, `scan_plan.*discarded` | кадр снят не в ожидаемом окне или отброшен после retune |
| DETECTOR | `signal_analysis.activity_observed`, `signal_analysis.frame_rejected`, `rf_decision.transition` | detector не получил кадр либо quality gate отклонил его |
| NORMALIZER / EVENT BUS | `signal_processor.event_published`, `signal_processor.event_publish_failed` | наблюдение не стало общим RF-событием либо публикация завершилась ошибкой |
| SIMPLE UI | `signal_processor.situation_changed` и карточка «АКТИВНОСТЬ» | backend обновился, а presentation не отобразил снимок |

`acquisition.capture_requested` и `acquisition.frame_captured` ограничены по
частоте записи, чтобы не заполнить диск. `signal_analysis.activity_observed`
пишется для RF-кандидата, а `signal_processor.event_published` — при реально
принятой публикации. Источником истины для непрерывности capture служат растущие
`seq`, свежий `age` и отсутствие роста `dropped`.

## 3. Быстрая локализация неисправности

### Нет устройства или нет RF-кадра

- Проверьте, что запуск не содержит `--demo`.
- В профиле должны быть `enable_real_adapters: true`, включённый адаптер и точное
  подключение (`RTLSDR:<index>`, `HACKRF:<serial>` или один `COM<n>`).
- Проверьте драйвер, USB-питание, антенну и кабель.
- Для RTL-SDR убедитесь, что выбранное окно находится в аппаратном диапазоне.
  Обычный RTL-SDR не принимает 2,4/5,8 ГГц без совместимого внешнего тракта.
- Один перестраиваемый приёмник не наблюдает весь широкий диапазон одновременно;
  проверьте активное окно и scan plan.
- При первом Live-запуске с готовым физическим приёмником ALGA VECTOR запускает
  компактный preset `field_priority`. Он включает только те участки, которые
  подтвердил профиль текущего приёмника. Для обычного RTL-SDR участки 2,4 и
  5,8 ГГц честно исключаются; они требуют совместимого тракта, например HackRF.

### Кадр есть, но detector отклоняет его

- Смотрите `reason_code`, noise floor, peak excess/SNR, число history frames,
  non-finite bins, stale age и retune/warm-up flags.
- Для полевого поиска используйте `detection_sensitivity: high`.
- Не изменяйте display-only `threshold_level`: это линия спектра, а не порог
  детектора.
- Сравните тест с антенной и на согласованной нагрузке/без антенны, не меняя
  остальные параметры. Это помогает отличить реальный вход тракта от внутреннего
  шума, но не классифицирует источник.

### Candidate есть, normalized event отсутствует

Это ошибка fallback/normalization. Сохраните строки с одинаковыми `source_id` и
`sequence`. Неподтверждённая ненулевая аномалия должна пройти как общее
`RADIO_ACTIVITY_DETECTED`/`SUSPICIOUS_RF_ACTIVITY`, даже если классификатор не
узнал форму.

### Event опубликован, SIMPLE молчит

- Снимите `event_id`/`trace_id` и delivery counters.
- Отключите фильтр «Показывать только важное» только для дополнительной проверки:
  generic RF-активность должна быть видна и при включённом фильтре.
- Проверьте `signal_processor.situation_changed` и revision снимка.
- Если revision растёт, а экран не меняется, приложите support bundle и журнал.

## 4. Что записать в отчёт полевого теста

- версия приложения и SHA-256 сборки;
- точная модель приёмника, драйвер и антенна;
- Live/Demo provenance;
- center/span/sample rate/gain;
- sensitivity preset;
- scan window и dwell;
- время начала/окончания контрольного эпизода;
- последний успешный `seq` до события и первый после него;
- reason codes отказов;
- support bundle без raw IQ и точных координат.

Не публикуйте серийные номера, точные координаты объекта и необработанный полевой
журнал без отдельной проверки содержимого.
