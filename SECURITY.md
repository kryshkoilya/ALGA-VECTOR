# Политика безопасности ALGA VECTOR

## Поддерживаемые версии

Исправления безопасности готовятся для последней опубликованной версии.

| Версия | Поддержка |
|---|---|
| 0.7.x | Да |
| 0.6.x и старше | Нет, если отдельно не объявлено обратное |

Исторические portable-артефакты сохраняются для воспроизводимости, но не
должны использоваться как поддерживаемые рабочие сборки.

## Как приватно сообщить об уязвимости

Не создавайте публичный Issue, если проблема может:

- выполнить произвольный код;
- раскрыть пользовательские данные, координаты, конфигурацию или записи;
- обойти разделение Live/Safe/Demo;
- выдать simulated/stale данные за реальные;
- обойти fail-closed event policy;
- небезопасно открыть или настроить USB/COM-устройство;
- разрешить непредусмотренную передачу;
- повредить данные или конфигурацию;
- создать path traversal, command injection или unsafe deserialization;
- сделать support bundle неотредактированным.

Предпочтительный канал — **GitHub Private Vulnerability Reporting**:

1. Откройте вкладку **Security** репозитория.
2. Выберите **Report a vulnerability**.
3. Создайте приватный advisory.

Если Private Vulnerability Reporting недоступен, свяжитесь с владельцами
репозитория приватным каналом, указанным в профиле организации/владельца.
Не публикуйте технические детали до подтверждения безопасного канала.

В дереве проекта не указан отдельный security email, поэтому этот документ не
изобретает адрес, который может принадлежать постороннему лицу.

## Что включить в отчёт

- версия ALGA VECTOR и SHA-256 артефакта;
- Windows build и архитектура;
- способ запуска: source, portable или installer;
- режим: Live, Safe или Demo;
- тип устройства и версия драйвера/firmware/host tool;
- минимальные шаги воспроизведения;
- ожидаемое и фактическое поведение;
- оценка влияния;
- безопасный proof of concept;
- redacted logs/stack trace;
- наличие временного обходного решения.

Не прикладывайте без отдельного согласования:

- raw IQ и длинные spectrum recordings;
- точные координаты или адрес объекта;
- персональные данные;
- API keys, токены, пароли;
- полный пользовательский профиль;
- неотредактированный `.avsupport`;
- proprietary firmware или данные третьих лиц.

## Процесс обработки

Maintainers постараются:

1. подтвердить получение отчёта;
2. воспроизвести проблему в изолированной среде;
3. оценить затронутые версии и влияние;
4. подготовить исправление и регрессионный тест;
5. собрать новый артефакт и checksum;
6. согласовать срок раскрытия;
7. опубликовать advisory после доступности исправления.

Это best-effort процесс, а не договорной SLA. Если отчёт неполный или требует
физического оборудования, проверка может занять больше времени.

## Security boundaries проекта

ALGA VECTOR спроектирован как локальный receive-only инструмент:

- реальные адаптеры открываются только после явной настройки;
- discovery отделён от capture;
- Demo требует явного режима и маркирует simulated provenance;
- subprocess запускаются без shell, с timeout и bounded output;
- hardware worker изолирован от UI;
- event policy работает fail-closed;
- invalid config не должен перезаписывать last-known-good;
- support bundle локальный и не отправляется автоматически;
- raw IQ и spectrum arrays исключаются из штатного support bundle;
- HackRF contract не предоставляет TX API, signal-source mode, antenna power
  или RF amplifier enable.

Нарушение любого из этих свойств рассматривается как потенциально серьёзная
проблема.

## Проверка загруженного релиза

Скачивайте ZIP и `.sha256.txt` из одного GitHub Release. Проверьте:

```powershell
Get-FileHash .\ALGA_VECTOR-0.7.0-Windows-x64-onedir.zip -Algorithm SHA256
```

Для проверенного артефакта 0.7.0 ожидается:

```text
B40CF7C9CC6A0FBF9556888265D791DD8566C5CF4FDF7C7A7916BFA2E2A5316E
```

SHA-256 подтверждает целостность относительно опубликованного значения, но не
заменяет Authenticode. В отчёте сборки 0.7.0 Authenticode-подпись не заявлена.
Если Windows показывает предупреждение, не обходите его автоматически:
сначала проверьте источник, checksum и содержимое release.

## Локальные данные и приватность

- Используйте отдельный каталог данных с контролируемыми правами доступа.
- Не храните секреты в YAML-конфигурации или issue attachments.
- Перед передачей support bundle проверьте его вручную.
- Не публикуйте координаты базы, названия объектов и уникальные RF-записи.
- Ограничьте доступ к ADS-B JSON и журналам согласно локальной политике.
- Удаление/retention проверяйте на копии, если записи имеют доказательное
  значение.
- Не запускайте приложение или hardware tools от администратора без
  подтверждённой необходимости.

## Аппаратная безопасность

Программный release gate не подтверждает безопасность конкретного RF-тракта.
До подключения:

- проверьте допустимый входной уровень приёмника;
- используйте подходящие фильтры/аттенюатор;
- не подавайте питание или неизвестный сигнал на RF-вход;
- проверьте драйвер и firmware из доверенного источника;
- исключите конфликт с другим SDR-софтом;
- выполняйте hot-plug тесты в контролируемой среде;
- для HackRF используйте только заявленный receive-only путь;
- не считайте descriptor discovery успешным аппаратным acceptance.

## Достоверность и безопасность операторского решения

Ошибочная уверенность также является риском безопасности:

- частота и RSSI не подтверждают тип физического объекта;
- рост уровня не доказывает приближение;
- отсутствие RF-события не доказывает отсутствие источника;
- один bearing не даёт координату;
- ADS-B не является IFF;
- Demo не подтверждает реальную чувствительность;
- эвристический confidence не является probability;
- `MULTISENSOR_CORRELATED` не равен `TARGET_CONFIRMED`.

Не удаляйте эти ограничения из UI и документации без независимо
валидированной замены.

## Scope для security research

Разрешённое добросовестное исследование должно:

- выполняться на собственном оборудовании и данных;
- соблюдать применимое право;
- избегать воздействия на сторонние системы и радиосвязь;
- не использовать активное излучение, глушение или подавление;
- минимизировать доступ к реальным пользовательским данным;
- прекратиться при обнаружении непредвиденного воздействия;
- передавать результат приватно.

Эта политика не предоставляет разрешения исследовать чужое оборудование,
сети, радиосвязь или данные и не отменяет требования закона.
